# Pull Rebase (Pull Rebase)

## 이 옵션이 하는 일

`git pull` 명령어 실행 시 병합(merge) 대신 리베이스(rebase)를 사용할지 결정합니다. 리베이스를 사용하면 커밋 히스토리가 더 깔끔해집니다.

## 동작 방식

### 활성화 시 (ON)
- `git pull` 시 자동으로 `git pull --rebase` 실행
- 로컬 커밋을 원격 커밋 위에 재배치
- 선형적인 히스토리

### 비활성화 시 (OFF, 기본값)
- `git pull` 시 병합(merge) 사용
- 병합 커밋 생성
- 분기된 히스토리

## 사용 시나리오

### 활성화가 유용한 경우
- **깔끔한 히스토리**: 선형적인 커밋 히스토리 선호
- **개인 브랜치**: 개인 작업 브랜치
- **리뷰 용이**: 히스토리 읽기 쉬움

### 비활성화가 권장되는 경우 (기본값)
- **공유 브랜치**: 여러 사람이 작업하는 브랜치
- **안전성**: 병합이 더 안전
- **기본 동작**: Git 기본 동작 유지

## 알아야 할 것들

### Rebase vs Merge

**Rebase**:
- 커밋을 재배치
- 선형적인 히스토리
- 히스토리 재작성 (주의 필요)

**Merge**:
- 커밋을 병합
- 분기된 히스토리
- 안전하고 추적 가능

### 공유 브랜치 주의

**중요**: 이미 푸시한 커밋을 리베이스하면 안 됩니다:
- 히스토리가 변경됨
- 다른 사람에게 문제 발생
- 공유 브랜치에서는 병합 사용 권장

### 안전한 사용

리베이스는 다음 경우에 안전합니다:
- 로컬 브랜치만
- 아직 푸시하지 않은 커밋
- 개인 작업 브랜치

## 자주 발생하는 오류

### "Updates were rejected" 오류
**원인**: 리베이스로 히스토리가 변경되어 푸시 거부

**해결 방법**:
1. `git pull --rebase` 사용
2. 또는 `git push --force` (주의: 공유 브랜치에서는 위험)

### 히스토리가 복잡해짐
**원인**: 병합 커밋이 많이 생성됨

**해결 방법**:
1. `pull.rebase` 활성화
2. 또는 수동으로 `git pull --rebase` 사용
